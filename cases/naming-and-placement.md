# Naming and subject placement

Standing: reconstruction of an actual conversation episode, with interpretations identified below. This was not an explicit invocation of the SDS skill files or a controlled test of the method.

## Source event

The user sought a name broad enough for the project, literal and simple, naming an entity. Understanding Machine was initially favored and later rejected. The discussion moved through instruments and directors, with depth and literalness preferred over invented metaphors. Larger batches of names produced more useful feedback.

The user then requested that names remain general but claim less. System Kit received a positive judgment. The user subsequently asked for a lower claim than kit. After considering alternatives, the user proposed subjectsystems, accepted the interpretation, and authorized setup of the already-created repository.

The later [custom-system decision](../decisions/0003-custom-systems.md) changes the repository architecture beyond this initial relevance map. The episode remains evidence; separate local systems can develop different results from it, as the [custom-output demonstration](custom-system-outputs.md) shows.

## What the episode establishes

| Item | Standing |
|---|---|
| System Kit received a positive judgment | Directly recorded selection feedback |
| The user then requested a lower claim than kit | Directly recorded revision to the naming criterion |
| The user proposed subjectsystems and approved setup | Directly recorded choice and authorization |
| Kit suggests pieces prepared for use | Assistant's linguistic interpretation in the discussion |
| Subject Systems can mean systems organized around subjects | Proposed reading accepted as the project direction |
| The user always prefers low-claim names | Not established; the evidence concerns this naming task |
| The chosen name proves the project's structure is optimal | Not established |
| More names or SDS generally improve naming | Not established by this episode alone |

The selection of a whole name does not show that every property of the name caused the preference. The later request supplies additional evidence about the criterion. The preference does not require lowering the ambition of the project itself.

## One episode, several subject uses

| Subject | Material used | Work changed by that material |
|---|---|---|
| Design | Candidate names and successive revisions | Generate or revise forms in response to concrete selection |
| Preferences | Contextual positive and negative judgments | Distinguish observed choices from explanations of those choices |
| Goals | The requirement to remain general while claiming less | Refine what the naming task is trying to achieve |
| Judgment | A new criterion concerning readiness implied by kit | Reconsider an initially acceptable candidate under the revised standard |
| Representation | The subject-first reading of Subject Systems | Organize the repository through subjects, with systems as contributors |
| Relevance | Different uses of the same selection episode | Place the episode under several subjects without copying its identity |
| Memory | Earlier approval and later revision | Preserve history without treating the earlier candidate as the final choice |

The SDS README describes generating alternatives, selection, refinement, and requirements discovered from design. This episode is a retrospective example of that kind of pattern. Its relevance is grounded in the structure of the episode, not merely in shared terminology.

## Concrete consequence in this setup

The current README uses a structural description. Subject pages are the primary entry points; source systems appear as contributors. The decision record retains the distinction between a modest name and ambitious development. System Kit remains part of the history and does not regain the status of chosen name.

This is a documented change from a selection episode into repository organization and wording. It is not evidence for a universal naming theory or for runtime effectiveness of the source systems.
